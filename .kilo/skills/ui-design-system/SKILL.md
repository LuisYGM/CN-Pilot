# ui-design-system

Deriva la dirección visual del objetivo, público, posicionamiento, contenido, identidad y fidelidad esperada. No uses tokens o componentes por costumbre ni conviertas azul, sans-serif, cards, radios y gradientes en una solución universal.

En Greenfield con nueva dirección, establece el baseline reusable BF-057 sin convertirlo en librería enterprise; sus primitives son muestras neutrales, no features hipotéticas ni obligación de usarlas en páginas. Después añade solo decisiones/components específicos de páginas/flows confirmados. En Existing, hereda la fuente vigente antes de proponer extensiones.

Usa `.cn-pilot/config/responsive.json` en proyectos nuevos y la configuración vigente en proyectos existentes. Los breakpoints no obligan a crear overrides.

No conviertas una landing sencilla en una librería empresarial.

## Design System First (BF-046)

Para una experiencia visual nueva o rediseño material, sigue `.cn-pilot/CORE.md` BF-046: foundations y UI Kit visual/evaluable responsive, Internal System Review y Human Visual Approval antes de la primera página high-fidelity. Un kit pequeño puede bastar; no generes foundations/componentes de dominio hipotéticos ni un framework universal, y no conviertas el kit en una Home/landing. Tras aprobarlo, las páginas consumen tokens/global styles/components compartidos. Existing reutiliza la fuente aprobada y expone solo adiciones pertinentes; no crea un sistema paralelo ni pide una aprobación redundante si el sistema actual no cambia materialmente. La aprobación del Kit no amplía scope ni publica; con full implementation ya confirmada puede iniciar Product, y el page review ocurre allí sobre el candidato representativo cuando sea material (BF-057). Design-only mantiene su revisión en Project Artifacts.

### Reusable visual baseline (BF-057)

Presenta el Kit como sistema/specimens, nunca como la Home: no uses la navegación/header del sitio como encabezado; agrupa identidad/logo como specimen `Brand/Identity`. Cuando CN define una palette nueva, separa `Brand Palette` de `System Palette` y establece roles semánticos `primary` y `secondary`; estos aliases no reducen la marca a dos colores. La `System Palette` representa neutrals, background, surface, text, muted text, border, success, warning, error, info y focus según el producto. Incluye cada color que usa la interfaz aprobada. Si Product descubre un color sistémico ausente, añade el token al Kit y sincroniza Product en el mismo cambio; no hardcodees colores de sistema solo en página.

Muestra H1–H6 con el mismo texto de prueba para comparar jerarquía y define tokens/variables reales para los seis; si se elige escala fluida, usa el contrato `clamp(<min-px>, <expresión fluida>, <max-px>)` cuando corresponda. Los headings de página consumen tokens aprobados, no valores ad-hoc para el mismo role. Una necesidad compositiva legítima (display hero, título editorial/proyecto, compacto de datos o acento) puede tener variant explícita, derivada de la dirección, con propósito y reusable cuando corresponda; intégrala al sistema y úsela desde Product. No prohíbas expresión creativa ni dejes tamaños aislados sin relación sistémica. Registra familias `display/heading`, `body` y `UI/accent` solo cuando el proyecto las requiera, con escala y line-height tokenizadas. Usa tipografía y spacing fluidos cuando mejoren el rango responsive; muestra spacing de sección y el `container/max-width` real. En Greenfield, un container principal >1200px es un punto de partida común, no regla fija: deriva el valor del contenido/composición/viewport. No impongas una familia o dimensión por plantilla.

Si Greenfield no proporciona tipografía y elegirla tiene relevancia visual, considera unas pocas fuentes web plausibles (Google Fonts u otra fuente apropiada) según marca, sector, legibilidad/idioma, weights, performance y licencia; no es obligatorio usar Google Fonts ni investigar extensamente. Una fuente no-system elegida en Product debe tener carga/import/self-host verificable y fallback deliberado. UI Kit y Product deben coincidir. En Existing/microcambio conserva la fuente y no investigues tipografía sin motivo.

Como primitives neutrales incluye botones (`primary`/`secondary` y link action si aplica; focus/hover/disabled/loading pertinentes), una card reusable, un accordion accesible de FAQ (single-open, primer item abierto por default y transición sutil) y un specimen de form con text/select/textarea/radio/checkbox/button, labels e instrucciones. El accordion debe abrir/cerrar suavemente, sutil y brevemente con continuidad espacial; no abrupto, largo, bounce ni overshoot. Preserva teclado, estado/ARIA y el contrato single-open/first-open; `prefers-reduced-motion` elimina o reduce la transición sin cambiar el estado ni ocultar contenido. Aplica la misma contención a drawer/dropdown/tabs/hover/state transitions cuando el movimiento aporte valor, no animes todo. Muestra required/focus/disabled/error/success cuando corresponda a cada control. Preserva el patrón de una referencia Approved/Strict o Existing cuando difiera. Estos specimens no implican que la página requiera cards/FAQ/form: el patrón de cada página se deriva de propósito y contenido. Project-specific widgets solo con use cases confirmados. No rellenes el Kit con placeholders visibles, fake data o CTAs reales de página.

## Disciplina visual

Construye jerarquía visual deliberada: una prioridad dominante, escala tipográfica razonable, spacing con ritmo y composición que no dependa de cards genéricas, gradientes o headings enormes. Usa color con función —acción, estado, contraste o agrupación— y evita saturar la interfaz sin propósito. Asimetría, contraste y tratamiento editorial son herramientas cuando sirven al contenido, no fórmulas universales.

En una crítica visual detecta anti-patterns concretos —jerarquía plana, densidad accidental, alineaciones inconsistentes, controles con estados incompletos, texto difícil de leer, responsive que aplana la composición— y propone correcciones acotadas. El refinamiento es bounded: una pasada agrupada y una confirmación suelen ser preferibles a loops indefinidos; preserva contenido aprobado y scope del proyecto.

## Creative Direction proporcional

Activa esta profundidad cuando existan decisiones visuales significativas; una sección pequeña o un ajuste localizado puede usar solo el sistema vigente. BF-046 define un gate visual separado de UI Kit, pero no convierte `Creative Direction` en un formulario/serie de variantes: resuelve allí la tesis y reglas antes de sistematizarlas.

1. **Jerarquía de fuentes.** Distingue identidad aprobada (logo, tipografía, colores o restricciones normativas), convenciones compartidas vigentes, composición heredada que puede revisarse, preferencias orientativas e inspiración externa. Registra qué se conserva y qué está abierto, con evidencia o limitación de acceso; una pantalla antigua no es automáticamente marca, y una referencia externa no desplaza la identidad aprobada.
2. **Tesis visual.** Expresa brevemente el carácter que sirve al público, posicionamiento y contenido; traduce cada adjetivo importante en consecuencias comprobables de jerarquía, imagen, color, tipografía, ritmo, composición o componentes. Si «premium» o «moderno» no cambia ninguna decisión observable, no aporta dirección. Distingue restricciones de preferencias y decisiones propuestas de decisiones aprobadas.
3. **Referencias con autoridad.** Sigue el registry BF-048 (`authority`, `fidelity`, `scope`, `preserve`, `may adapt`) antes de decidir `adopt`, `adapt` o `discard`. Con `INSPIRATION`/`DIRECTIONAL` de terceros, extrae principios sin clonar layout ni reutilizar assets/copy. Un `APPROVED VISUAL REFERENCE` o `STRICT IMPLEMENTATION REFERENCE` autorizado gobierna su scope: no reabras Creative Direction ni apartes el layout por novedad; las adaptaciones técnicas permitidas deben respetarlo. Authority visual no implica derechos para copiar assets/textos. Si referencias equivalentes se contradicen materialmente dentro del mismo scope, escala una pregunta breve por Dev Lead.
4. **Reglas y anti-reglas.** Define solo las que vuelven implementable la dirección: jerarquía, tratamiento de imagen, carácter del spacing, comportamiento tipográfico, grid, uso del color y carácter de componentes. Las anti-reglas identifican específicamente lo que volvería genérico o incoherente *este* proyecto; no prohíbas universalmente cards, gradientes, asimetría, motion ni tipografía grande.
5. **Integridad de recursos.** Sigue el contrato canónico de recursos visuales de `.cn-pilot/CORE.md`: distingue assets gráficos de imágenes representacionales, no resuelvas fotos/espacios/productos con SVGs genéricos y comunica gaps materiales fuera del canvas. En Existing, continuidad incluye la biblioteca de imágenes/ilustración y su tratamiento, no solo tokens.
6. **Estrategia de medios.** Sigue BF-045 como parte del visual fingerprint de BF-043: deriva tipo/densidad de recursos de producto, contenido y Existing, y busca riqueza contextual incluso si no hay fotografía. Ilustración, gráfico, textura, pattern, diagramas, vídeo, motion o composición tipográfica pueden aportar; ninguno es obligatorio. No conviertas la falta de imagen en una receta tipográfica ni en una invitación a llenar espacio con decoración genérica.
7. **Ruta y autoridad.** Si hay varias direcciones plausibles que cambiarían materialmente el resultado, selecciona una ruta visual y explica sus tradeoffs; no generes tres variantes ni maquetas por obligación. Si el criterio ya es claro, avanza. Distingue design system global (Theme Styles, tokens, clases compartidas, biblioteca Figma, style guide) de composición local; no cambies recursos globales para satisfacer un detalle de página sin alcance y autorización.
8. **Prototipo y motion.** Si el scope es Design-only/handoff o el usuario pidió prototipo, el high-fidelity web prototype se entrega como HTML/CSS/JS responsive en `project-artifacts/design/pages/`; preserva esa vía y no crees Product fuera de scope. Si full implementation ya es scope, tras el gate del UI Kit Frontend implementa directamente la primera página candidata en Product; no construyas una página completa duplicada en Project Artifacts para volverla a implementar. Un prototype separado solo si interacción/dirección compleja es esencial para aprobación o se solicita explícitamente. El contenido aprobado sigue como fuente editorial. Motion solo si intención/beneficio UX lo justifican, con accessibility/performance/reduced-motion; si es material el Kit muestra los specimens necesarios, no un Motion System universal. Usa `motion-interaction` para interacción avanzada, no para imponer tooling.

## Diversidad visual fundada (BF-043)

Aplica esta profundidad en Greenfield, marcas conceptuales o cuando la identidad esté realmente abierta; no conviertas la variedad en novedad obligatoria. Deriva un visual fingerprint observable del sector, producto/servicio, público, posicionamiento, objetivo, personalidad, contenido, contexto de uso y assets. Según el proyecto, resuelve intencionalmente paleta, tipografía, imagen/art direction, composición, densidad, ritmo, geometría, carácter de componentes, iconografía, bordes y modelo de contraste. No es un formulario, score ni documento nuevo obligatorio.

- **Color con grounding:** vincula la paleta a una razón del proyecto, no solo a que parezca profesional, premium, limpia o actual. Si la identidad está abierta y existen alternativas genuinas, compara internamente más de una familia cromática plausible y selecciona una según el contexto. No presentes variantes por obligación ni exijas que el usuario elija una paleta sin preferencia material. Cualquier familia puede ganar por una razón suficiente; verde, crema, oliva, acid green, serif, editorial, minimalismo o eyebrows no están prohibidos.
- **Comprobación anti-default/swap:** antes del prototipo pregunta internamente si al cambiar logo, copy y fotos la dirección seguiría encajando casi intacta en un sector no relacionado. Si sí, refina solo los ejes que sigan genéricos. Si varias decisiones cómodas se agrupan —por ejemplo warm-neutral + green/olive + serif editorial + uppercase eyebrow + gran heading + whitespace amplio— comprueba si las exige el proyecto. Esta señal invita a revisar grounding; no es una blacklist.
- **Sin originalidad artificial:** conserva UX, conversión, accesibilidad y legibilidad. No fuerces paletas distintas, composiciones experimentales, referencias externas, múltiples propuestas ni una métrica de originalidad. Investiga referencias solo si aporta valor; extrae principios sin copiar.
- **Existing, continuidad primero:** ante identidad vigente, Design System, páginas ya resueltas o referencia aprobada, inspecciónalos y conserva tokens, tipografía, color, spacing, geometría, imagen, componentes y carácter. `Continuity > novelty`: diversity nunca obliga a rediseñar un Existing ni a apartar una referencia aprobada.

Las heurísticas existentes de jerarquía, ritmo, bounded refinement y detección de anti-patterns siguen vigentes; se aplican al contexto, no como otra plantilla segura. Conserva la atribución de esta skill sin cambios.

Antes de entregar, contrasta tesis y reglas con al menos la composición prioritaria y su responsive: ¿son visibles las decisiones, respeta identidad y copy, es viable en el stack, conserva editabilidad y evita dispositivos visuales inventados? Documenta adaptaciones técnicas relevantes sin sustituir `visual-parity-review`, `webapp-testing` ni Human Visual QA. Detén el refinamiento cuando queden microajustes de bajo retorno, pero no ignores una diferencia material.

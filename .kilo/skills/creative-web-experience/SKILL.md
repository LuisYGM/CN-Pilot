# creative-web-experience

**Owner: Diseñador UI/UX.** Responde «¿qué hace que esta experiencia sea propia, memorable, visualmente rica y difícil de intercambiar con otra marca?». Define ambición, research acotado, intención visual y Creative Quality Gate; coordina conceptualmente sistema, composición, media, motion y UI Kit. No implementa frontend ni sustituye esas capacidades. Stack-agnostic.

## Trigger y autoridad

Default para una **public web** nueva o rediseño visual material: Home, landing, About, servicios, product marketing, portfolio/case study, ecommerce storefront/product marketing, corporativa, hospitality, restaurantes, real estate, arquitectura, agencia, NGO, B2B, industria/logística, tecnología, campañas y experiencias editoriales públicas; aplica en HTML, frameworks, Laravel frontend, WordPress, Bricks, Elementor, WooCommerce y otros stacks.

No es default para SaaS application UI, dashboard, CRM, backoffice, intranet, portal interno, data-heavy ni admin: usa `application-ui`. En SaaS híbrido, Home pública usa esta skill y dashboard `application-ui`. Excluye microcambios, CSS/metadata/copy localizado, Existing con continuidad cerrada y reproducción Approved/Strict que prescribe completamente el resultado. Existing conserva `continuity > novelty`; BF-048 Approved/Strict gobierna su scope/fidelity y la novedad solo cabe en `may adapt`/scope abierto.

En sitios multipage la primera dirección/rediseño establece lenguaje creativo; páginas derivadas consumen sistemas, referencias, typography, media language y motion language aprobados. No repitas scouting ni redefinas sistemas salvo necesidad material nueva. `page-composition` define silueta específica de cada página.

## Ambición y brand-led exploration

Infiere, no preguntes ni publiques como score por rutina, un nivel de ambición apropiado: **QUIET, REFINED, EXPRESSIVE o IMMERSIVE**, desde identidad, sector, público, posicionamiento, contenido, objetivo/conversión, recursos, contexto, referencias y restricciones. QUIET no es genérico; no fuerces IMMERSIVE, experimento, efectos ni sacrifiques UX/conversión/accesibilidad/performance.

Con identidad/logo/material suficiente, analiza **brand grammar** observable: curvas, ángulos, proporciones, strokes, inclinación, remates, geometría, ritmo, repetición, contraste, carácter tipográfico y relaciones. Traduce propiedades útiles a decisiones visuales concretas —radios, strokes, iconos, masks, separadores, patterns, crops, containers, botones, geometría, transiciones o trayectorias— solo con intención; no uses fórmulas universales.

Conserva anti-default/swap test. Añade dos pruebas: **anti-template**: si cambian logo/copy/fotos, ¿la propuesta se vendería casi intacta a otro sector? Si sí, sigue genérica. **anti-copy**: con referencia Inspiration/Directional, si se cambia la marca del proyecto por la de la referencia, ¿podría confundirse razonablemente con ella? Si sí, extrajiste demasiado poco: toma principios, no clones identidad/composición. Approved/Strict mantiene authority BF-048.

## Creative Input Audit y gaps

Antes de diseñar, audita proporcionalmente identidad/logo/brand assets, contenido, media, referencias/authority, typography/iconography vigentes, proof/trust material, claims verificables, objetivos/conversión y restricciones/Existing. No hagas una auditoría extensa ni exijas artefactos: clasifica internamente cada gap relevante:

- **READY:** suficiente información/authority para una buena decisión autónoma.
- **ENRICHABLE:** se puede seguir, pero input/respuesta humana disponible podría mejorar materialmente visual quality, differentiation, trust, content, composition, media, storytelling o conversion.
- **BLOCKED:** falta un input/authority/decision imprescindible para proceder correctamente.

**Poder continuar no prueba suficiencia creativa.** No preguntes por decisiones reversibles (spacing, grid, radius, cards, breakpoints, technical choices); resuélvelas profesionalmente. Un gap ENRICHABLE puede justificar una **Creative Opportunity Question** no bloqueante si la respuesta realmente cambia calidad/outcome y se puede actuar dentro del scope. Primero inspecciona y ejecuta research read-only disponible; luego Jefe de proyecto agrupa en una ronda las oportunidades iniciales más influyentes, no un cuestionario exhaustivo ni una pregunta por cada dato ausente. Pregunta por resultado humano; usa UI nativa si existe, permite `Custom/otra` y normalmente `Decide tú`. BLOCKED también se consulta. Si la persona responde `Decide tú`, decide sin reconfirmar. Solo un gap material nuevo imposible de anticipar puede justificar segunda ronda. Si ya autorizó contenido/assets/una opción no repitas permiso.

## Reference & Asset Coverage

Antes de declarar que discovery/inputs bastan, inspecciona proporcionalmente fuentes existentes: brief/auditoría, contenido, identidad, librerías de media, referencias Approved/Strict y documentos índice (`REFERENCES.md`, `REFERENCIAS.md` o README) si existen. Identifica las familias materiales (p. ej. branding, producto/lifestyle, campañas, collage, vídeo, web references, tipografía); inspecciona lo representativo y material, no cada archivo repetido. Mantén prioridad: material del usuario/cliente → referencias Approved/Strict → sistema/recursos Existing → investigación propia → convenciones generales.

Si un índice/documento incluye URLs que puedan cambiar la dirección, abre e inspecciona las relevantes antes de afirmar Reference Coverage completa, señalando brevemente fuente, autoridad propuesta, principio útil/descartado y limitación. Omite links duplicados, irrelevantes o administrativos. Si una URL material no funciona o no es accesible, no finjas inspección: explica el gap y pregunta solo si impide la decisión; puede seguirse por otra vía solo si el usuario descarta esa referencia o el scope no depende de ella. Sin referencias no inventes un registro ni bloquees discovery.

Reference research y asset research son distintos: una web externa inspira principios, pero sus medios/copy no se reutilizan como assets del proyecto. Para provenance/licencias y opciones concretas rige `visual-art-direction`; no descargues mirrors ni copies assets sin autorización.

## Research acotado que debe ejecutarse

Si es public web Greenfield/rediseño material, no hay dirección Approved/Strict suficiente ni referencias aportadas/vigentes suficientes, **ejecuta** una sola ronda de reference scouting antes de converger. Comprueba las tools realmente disponibles en el runtime (permission `allow` no prueba que una tool esté expuesta): si existe `websearch`, invoca al menos una búsqueda dirigida y usa `webfetch` para abrir las fuentes relevantes; URL directas conocidas no sustituyen search si el tool existe. Explora sector y atributos/lenguajes visuales (no solo competidores); inspecciona normalmente 3–6 fuentes (máximo seis). Del handoff registra source realmente abierta, authority propuesta (Inspiration/Directional), principios observados, qué descartas y por qué. Referencias aportadas suficientes evitan búsqueda innecesaria; research propio jamás es Approved/Strict. Si `websearch` no está expuesto, no digas que está unavailable sin evidencia: usa el read-only webfetch disponible para inspeccionar fuentes accesibles cuando sea posible, revela que search tool no estaba expuesto y limita la afirmación a las fuentes que sí abriste. Si no hay herramienta/acceso web, declara la limitación real.

Opera el fallback, no solo lo reportes: cuando `websearch` no se expone pero `webfetch` sí, ejecuta scouting directo leyendo 3–6 fuentes relevantes y accesibles desde el contexto/conocimiento profesional; indica explícitamente que es exploración directa, no resultados de una search. No uses páginas de resultados vacías como evidencia. Si no hay ninguna web tool, registra la limitación.

Cuando no haya brand font ni Approved/Existing font que preservar, si hay acceso a fuente web fiable **ejecuta font discovery**, no basta con decir que se consideró. Verifica la tool disponible; explora normalmente 3–5 familias y consulta las páginas/datos fiables de sus fuentes, Google Fonts si conviene. Compara personalidad, display/body, legibilidad, idioma/caracteres, weights, variable axes, contraste, performance, disponibilidad/licencia. Selecciona una dirección; registra candidatas, elegida/razón, pesos, source/licencia comprobada y lo que no pudiste validar. Carga/valida la selección para el destino cuando el scope permite implementación. Inter/system/Arial/Georgia pueden ganar por motivos observables, no por default. Si no hay web/source fiable, comunica el límite y decide desde el contexto local.

Si un specimen page solo entrega HTML shell y no facilita comparar familias, consulta datos oficiales de la fuente (p. ej. catalog metadata/CSS API para pesos/ejes y el archivo LICENSE del repo de la familia) antes de cerrar discovery. Una page abierta o nombres de familia no demuestran que comparaste pesos/licencia. Si el fallback oficial también falla, registra el error y deja explícito que solo puedes sugerir dirección provisional, no aprobarla para producción ni estabilizar el gate si la licencia/selección es material.

Inspecciona assets reales/authority antes de clasificar **MEDIA GAP**: faltan imágenes/material y media editorial/representacional mejoraría materialmente el resultado. Es ENRICHABLE, no orden de insertar foto ni saltar a shapes/text. Informa a Jefe de proyecto con función concreta. La ronda agrupada presenta elección clara: buscar medios solo si el runtime puede realizar búsqueda de candidatos en este momento; generar solo si el generador/capability existe; la persona aporta assets; seguir sin foto con dirección gráfica; `Decide tú`; `Custom/otra`. Un capability futuro/condicional **no** cuenta como opción ejecutable: si search/generation no están disponibles, omítelos de la lista y declara la limitación brevemente fuera de ella. No mezcles elecciones independientes de media/contenido en una opción exclusiva; pueden contestarse separadamente en el mismo intercambio corto. Una exploración read-only de fuentes/candidatos no es aprobación de uso. Si elige búsqueda, aplica `visual-art-direction` con art direction concreta (subject, framing, environment, tone/light, crop/orientation/role), verifica source/licence y provenance. Incorporar assets requiere rights y scope/approval; generación real queda `ORIGINAL_CREATED`. “Aportaré imágenes” deja assets pending y permite trabajo independiente. No inventes capacidad o representación.

Si media no es material o la persona elige no usarlo/decide delegarlo, resuelve intencionalmente. Sin fotografía adecuada, considera visual moment gráfico basado en identidad (fragmentos de isotipo, geometría, trazos, patterns, composition tipográfica, masks, color fields, branded shapes, collage o sistemas ilustrativos). No finjas personas, productos, espacios, mapas, datos, instalaciones o arquitectura reales sin evidencia.

Cuando hay muchos iconos funcionales, prefiere una familia profesional coherente por proyecto/sistema; logos/brand marks pueden usar fuente separada apropiada. Posibles opciones a validar según stack/necesidad: Lucide (ISC; paquetes vanilla/framework y tree-shaking documentados), Tabler Icons (MIT; sistema consistente 24×24/stroke 2), Phosphor (MIT en su repositorio core; estilos/weights como vocabulario alternativo) y Simple Icons (CC0 copyright para iconos de marcas; no concede derechos de trademark). Selecciona según necesidad, verifica fuente oficial/licencia/consumo antes de formalizar nombres y no fijes versiones. No instales globalmente ni todas las librerías; los términos del icono no eliminan posibles derechos de marca registrada. Custom SVG se justifica por identidad, ausencia de concepto en el pack o lenguaje definido; comparte grid, stroke/fill, peso, esquinas, alineación óptica, viewBox, sizing y semántica. No inventes iconos inconexos.

Sin web/capability, no bloquees: informa brevemente qué research no pudo hacerse, usa identidad/contenido/recursos disponibles y decide profesionalmente. No afirmes investigación, disponibilidad o licencia no verificadas. Scouting es una ronda acotada, no un estudio por página.

## Content Enrichment Opportunity

Si copy escaso limita materialmente storytelling, trust, diferenciación, recorrido o módulos, clasifica ENRICHABLE aunque se pueda montar una página básica. Jefe de proyecto puede agrupar una **Content Enrichment Opportunity** con la pregunta de medios/otros gaps. No te conviertas en copywriter: si la persona quiere ampliar/reorganizar contenido, Jefe de proyecto enruta serialmente a Contenido / SEO con `content-page` antes de la siguiente etapa UX. Pueden proponerse proceso, organización de servicios, FAQ desde información confirmada, transiciones, framing, narrativa, explicación o contenido educativo sustentado; no introduzcas facts nuevos. Si solo cifras/clientes/testimonios/proyectos/certificaciones/premios/experiencia/cobertura/garantías/precios/resultados/partners permitirían proof o conversión, pregunta una sola vez si existe material verificable; nunca lo inventes. Aceptar `Decide tú` cubre estructura/copy derivable dentro del scope, no crea claims factuales ni amplía autorización.

## Concept Studies y divergencia visual real

En public web Greenfield/rediseño material con libertad compositiva real, no converjas directamente desde una primera idea ni describas las alternativas solo en texto. Normalmente produce **2–3 Concept Studies reales** (dos si solo existen dos direcciones con sentido; nunca más de tres por defecto). Si el producto/usuario ya fijó una dirección Approved/Strict o el sistema Existing aprobado resuelve la composición, usa su fast path, no generes conceptos artificiales.

Cada Concept Study es un pequeño artefacto HTML/CSS/JS ejecutable/evaluable (o stack ligero que el proyecto ya usa) bajo `artefactos/diseno/conceptos/concepto-a/`, `concepto-b/`, etc.; crea la carpeta en el primer concepto. Incluye shell/header suficiente, hero y 2–3 secciones que expresen su gramática visual, copy disponible/responsable, tipografía/media pertinente, motion behavior observable suficiente para evaluar el fingerprint público y una transformación mobile representativa. No exige implementar una Flagship completa por concepto. No es moodboard textual, screenshot, UI Kit, Flagship final, Product ni una Home completa. El usuario debe poder reconocer «cómo se siente» cada opción abriendo el artefacto.

Los conceptos comparten brief, contenido y autoridad de referencias pero difieren en **varias** decisiones macro: composición/jerarquía, relación type-media, ritmo/densidad, storytelling/orden, tratamiento espacial, carácter tipográfico y motion/interaction cuando sean parte de su fingerprint. Cambiar solo color/fuente, construir copias con el mismo hero/card-grid o disfrazar un template no es divergence. Mantén contenido real; nunca Lorem Ipsum ni claims inventados. Reutiliza assets PROVIDED/EXISTING; referencia externa inspira y no concede derechos. Cada Concept Study de dirección pública demuestra motion intent observable suficiente para comparar entrada, scroll behavior y momento principal; una nota de “planned animation” no cuenta. No requiere tres secuencias Flagship completas.

Los estudios muestran el contraste visual sin matrices screenshot: desktop orienta composición y motion; mobile demuestra adaptación de Hero, región compleja e intent de movimiento. No construyas cada breakpoint ni una página completa tres veces. En public web abierta motion es criterio obligatorio de dirección, no se omite por considerarla decorativa/minimal ni se resuelve con anotación textual; cada specimen es proporcional y evaluable. `NONE/static` solo es válido por opt-out explícito, authority Approved/Strict incompatible o constraint material que Jefe resuelve. No generes Kits/component libraries para cada alternativa.

## Human Creative Review y Visual Synthesis

Diseñador entrega los Concept Studies y una explicación breve de qué diferencia cada dirección, qué referencias/familias influyeron y qué limitación aplica a Jefe de proyecto; Jefe consolida la única decisión humana. La persona puede elegir un concepto, mezclar piezas, rechazar todos o delegar con «Decide tú». Si rechaza todos, agrupa solo el motivo/cambio que alteraría materialmente la dirección; no regeneres variantes idénticas ni repitas research sin evidencia nueva. No fuerces una elección entre alternativas si ya delegó; recomienda y justifica brevemente. No hagas implementation ni cherry-pick/merge entre worktrees para obtener una mezcla.

Tras la selección/mix, la **Visual Synthesis** convierte esos elementos en una gramática única y coherente: conserva con intención los rasgos escogidos y los sistemas/constraints aprobados; reconcilia contradicciones; no hace un promedio neutro ni añade rasgos de conceptos rechazados por accidente. Devuelve un handoff compacto de principios, composición/motion/media intent, referencias, elementos adoptados/descartados y gaps reales. Si los conceptos se ejecutaron en worktrees aislados por BF-062, se tratan como alternativas; la síntesis seleccionada es una unidad nueva, no una integración automática de ramas. La síntesis, no una exploración a medio cerrar, alimenta el UI Kit y el Flagship.

## Sistema definitivo y Flagship

Solo después de Visual Synthesis activa `ui-design-system`/`ui-kit-construction` cuando sus triggers correspondan. El Kit definitivo deriva de los principios sintetizados, no de una alternativa aislada ni de un sistema abstracto creado antes de explorar. Aplica los checks técnicos actuales de `ui-kit-construction` sin ampliarlos a requisitos de Header/Footer, Motion System o iconografía futuros. Haz la revisión interna del sistema antes de ensamblar una sola Flagship de página completa con `page-composition`; no generes una tercera/home paralela ni multipliques sistemas.

La Flagship usa el contenido disponible y la dirección aprobada, tiene responsive suficiente y muestra la experiencia final; no es Product runtime. Design-only la conserva en `artefactos/diseno/paginas/`. Cuando full Design+Implementation forma parte del scope, Human Visual Approval de la Flagship/Kit es el gate vigente antes de crear Producto o páginas derivadas; una aprobación inequívoca continúa el trabajo ya autorizado sin otra pregunta. El gate no publica. Después de aprobación, implementa el Flagship fielmente y deriva el resto de páginas solo si el scope las incluye. Una referencia Approved/Strict, sistema Existing resuelto, app UI o página derivada no rehace divergence/Flagship por rutina.

## Composición y motion intent

Toda región material justifica su función en journey/contenido y su composición; una lista de tres elementos no implica tres cards. Vocabulario posible, no checklist/templates: editorial grids, asimetría controlada, display type, capas, full-bleed/masked media, collage/mixed media, sticky/horizontal storytelling, scroll-linked media, grids modulares irregulares, split-screen, typography sections, floating media, paneles apilados, comparación interactiva, timelines visuales, sistemas ilustrativos, macro-details, secuencias cinematográficas, media por hover/focus, galerías, whitespace y progresión sticky. Elige lo que sirva contenido/marca/conversión y sea viable, usable y responsive. Para una Flagship pública abierta, diseña un memorable moment concept-linked; puede ser sutil, no es una cuota ni espectáculo.

En public web Greenfield/material redesign de dirección abierta, el Motion Experience Floor es obligatorio salvo opt-out explícito, autoridad incompatible o constraint material confirmada por Jefe. Diseña con composición: (1) hero/page choreography intencional, más que un fade total; (2) scroll-linked progression material que continúa después del Hero y busca deliberadamente una historia visual/narrativa del contenido; (3) behavior apropiado y diferenciado para las secciones principales; (4) microinteractions; y (5) un moment memorable concept-linked. No sirven `opacity/translateY/stagger` repetidos, Hero-only ni hovers solos; no existe quota de efectos. Minimal visual no es static: la intensidad puede ser sutil, conservando el floor. Un opt-out se aplica exactamente al behavior/scope pedido (“solo microinteracciones”, “sin scroll effects”, “sin motion”); “no GSAP” limita technology, no experience. Jefe lo registra y respeta sin persuadir. Expresa scroll/triggers, character/timing/states, mobile y reduced-motion; conserva calm zones. `motion-interaction` implementa; primero intent, luego la capability menor capaz de preservarlo. No fuerces IMMERSIVE ni animación constante.

Handoff motion material expone función, carácter/intensidad, choreography, scroll progression, roles de sección, memorable moment, calm zones, mobile/reduced-motion y capability solo si ya es material. Diseñador no entrega `none` por elección propia: Jefe resuelve excepciones de static/authority/constraint. Un `fade + translate + stagger` puede ser transición auxiliar, no el lenguaje completo de una Flagship abierta.

## Evidence-based Creative Quality Gate (pre-BF-063)

Antes de `VISUAL INTENT STABILIZED`, valida evidence sucinta: Reference/Asset Coverage, autoridad y content suficiente; 2–3 Concept Studies distintos con motion intent observable; Creative Review/Synthesis; UI Kit derivado; Flagship evaluable/ejecutable. En public web abierta, Flagship demuestra choreography, scroll progression material después de Hero, section-specific behavior, microinteractions, memorable moment y mobile/reduced-motion; “planned effects” en texto no sustituye ejecución. Static solo por opt-out, authority incompatible o constraint material resuelta por Jefe. Approved/Strict, app UI, Existing y páginas derivadas registran su fast path. Mantén anti-template/anti-copy y viabilidad/performance; no conviertas el gate en matrix de screenshots.

Cluster combinado de señales **Genericity Risk** (no errores aislados automáticos): hero split convencional sin razón; cards homogéneas; igual silueta/densidad/alineación en secuencia; system font por comodidad; media ausente sin decisión/gap; iconos improvisados; mismos reveal para toda sección; CTA genérico; gradient sin grounding; whitespace vacío; eyebrow+huge heading+three cards como fórmula; layout intercambiable de sector. Si este riesgo es material, una **Creative Refinement Pass focalizada** es obligatoria sobre evidencia concreta (type/composition/media/motion/rhythm/brand grammar/content); no decoración aleatoria.

Organiza el Creative Refinement Pass como un batch focalizado y reevalúa su evidencia al terminar. Una pasada puede bastar, pero no es un límite: si falta coverage material, los conceptos no son distinguibles, la Synthesis/Flagship sigue genérica o el resultado no corresponde al contexto, continúa el refinamiento específico necesario; no cierres la dirección solo por haber escrito una explicación. Detente cuando coverage, Concept Studies/Human Creative Review/Synthesis (si aplica) y Flagship coherente estén completos y no quede una mejora material pendiente. BF-059 limita iteraciones de bajo retorno, no justifica converger prematuramente. Si un scouting requerido falla por acceso real, registra la limitación y pregunta solo si esa referencia afecta una decisión; no simules research. Si una respuesta humana queda pendiente, conserva el gate fuera del canvas y avanza trabajo independiente. Solo entonces declara `VISUAL INTENT STABILIZED`; desde ahí BF-063: QA verifica, no rediseña. Ambición nunca degrada semántica, teclado/foco, reduced motion, visibilidad esencial, responsive/performance; marketing/static centrado en motion conserva contenido esencial ante fallo razonable de JS, sin exigir no-JS a toda SPA.

Entrega handoff compacto a Jefe de proyecto/Maquetador frontend que permite comprobar gates: fuentes de research inspeccionadas/principios/discards/authority; font candidates/selección/source; assets inspeccionados, MEDIA GAP/opción/provenance/limitaciones; content gap y decisión; alternativas macro/criterios/ganadora/descartes; motion brief; evidencia de distinctiveness/genericity refinement; y restricciones. No crea documento obligatorio ni escribe Project Context root. No implementa Product.
